그래서 오랜만에 기억을 다시 상기시키면서 특강을 듣던 중 의문이 생겼습니다.

#### Git stash?

처음들어보는 명령어였습니다. 파일의 변경내용을 일시적으로 저장해두는 것인데 적용 대상은 다음과 같습니다.

1. **작업 디렉토리(Working Directory)** 의 변경 내용

2. **스테이징 영역(Staging Area / Index)** 의 변경 내용

기본적으로 untracked는 저장되지 않지만 `-u `옵션을 통해 저장해둘 수 있습니다.

##### 근데 git add를 사용하면 staging에 올라가는데 stash는 그럼 어디에 저장해두는 걸까?

`stash`도 근본적으로는 `.git/object`에 저장되긴하는데 일반 브랜치가 아니라 `refs/stash`에 스택형태로 쌓인다고 합니다.

그래서 꺼내서 사용할때 `pop`이라는 명령어를 사용합니다.

하나의 `stash` 항목(`stash@{0}`)은 사실 **3개의 commit**으로 구성된다고 합니다.

1. **WIP 커밋 (Working Directory)** — 실제 작업 중 변경 내용

2. **Index 커밋** — 스테이징된 변경 내용

3. **Base 커밋** — 위 두 변경의 공통 부모 (stash 만들 당시의 HEAD commit)

즉, Git은 `stash`를 단순한 메모가 아니라, **commit으로 관리되는 스냅샷 구조**로 저장하는 것입니다.

몰랐던 이유를 생각해보니 저는 작업을 하던 도중 급하게 다른 작업을 할 일이 생기면 branch를 변경하였는데 이때 **smart checkout**으로 편하게 해버렸습니다...

##### 아 그럼 smart checkout이 자동으로 stash를 해주는구나!

결론부터 말하면 반은 맞고 반을 틀렸습니다.

```plaintext
If you click Smart Checkout, IntelliJ IDEA will shelve uncommitted changes, check out the selected branch, and then unshelve the changes.
```

`Intellij` 공식문서를 보면 `Intellij`는 `stash` 대신 `shelve`(IDE 레벨) 기능을 제공하고, 이것은 IDE가 패치(파일)로 저장합니다.

물론 설정을 바꾸면 `stash`를 사용할 수 있습니다.

추가적으로 예전부터 궁금했던 부분을 찾아보았습니다.

#### Git은 왜 불편하게 add 후에 commit을 하도록할까?

다른 형상관리 툴을 사용해보지는 않았는데 `Staging area`는 git에만 있는 구조라고 알고있습니다. 근데 `add`하는 과정은 항상 귀찮다고 생각해서 왜 필요할까에 대해 찾아보았는데 크게 세가지 이유가 있었습니다.

1. 일부분만 commit을 하고 싶을 때

`Staging area`라는 것이 없다고 가정해보았을때, ‘commit될 예정인 내용들’을 디스크에 저장해 둘 공간이 없으므로, commit할 때 어느 부분을 commit할지 한번에 결정해야 합니다.

한번에 어렵지 않게 결정할 수도 있지만 시간을 들여 생각해야 할 수도 있습니다. 시간을 들여 조금씩 commit할 부분을 결정한다고 하면, 그 시간동엔 저의 결정사항들은 메모리상에 존재하는 것입니다.

이때 프로세스가 갑자기 죽어버리면 제 시간이 다 날라가버리니 메모리에 두는 것은 위험한 일인 것입니다.

2. 충돌을 해결할 때

충돌을 해결해야 하는 상황에서도 비슷한 문제가 생깁니다. 여러개의 파일을 머지했는데 그 중 일부분에서만 충돌이 발생하면 그 일부분만 고치면 됩니다.

하지만 큰 규모의 충돌이 발생한 경우 이를 해결하는 것은 오래 걸리는 작업이고, 이것을 메모리에만 올려놓는 것은 위와 같이 위험성을 동반합니다.

따라서 이 정보 역시 `Staging Area`와 같이 디스크의 어떤 공간에 저장해두는 것이 훨씬 안전해집니다.

3. commit 다시 하기

Staging area가 없었다면 commit --amend 시에 Git은 “commit을 수정할 때 어떤 변경을 포함해야 하는지”를 **직접 전달받을 수단**이 없습니다.\
즉, `git commit --amend` 명령을 실행할 때마다 “이 파일은 바꿔줘, 저 파일은 그대로 둬” 하는 **패치(patch)** 정보를 명시적으로 넘겨줘야 했을 겁니다.

하지만 staging area가 있기 때문에 파일 하나가 누락되었어도

```plaintext
git add a.txt
git commit --amend
```

이렇게 하면 Git이 Staging Area의 내용 + 기존 commit의 나머지로 새 commit을 만들 수 있게 됩니다.
