### Fine-Tuning

오늘은 Unsloth를 활용해서 공식문서를 보고 gpt-oss를 fine tuning 해보았습니다.

### fine tuning을 하는 이유

- 도메인 specific한 정보들을 새롭게 추가가능
- model의 톤, response 스타일 커스터마이징 가능
- specific한 use case에 맞춰 정확성을 향상 가능

### VS RAG

1. Task specific도메인 specific한 task를 처리하기 좋습니다.
2. independance from retrieval외부 검색으로부터 독립적이기 때문에 장애가 생겨도 안정적입니다.
3. faster responses외부 DB를 사용하지 않고 스스로 추론하기에 response 속도가 더 좋습니다
4. custom behavior and tone모델 자체의 톤, 스타일을 커스텀할 수 있습니다.
5. reliable performance외부 DB로부터의 검색의 품질과 상관없이 우리 도메인에 더 적합한 성능을 보여줍니다.

### Is RAG Always Better Than Fine-Tuning?

fine tuning이 적절히만 된다면 NO

LoRA 파라미터를 잘못쓰거나 충분하지 않은 학습을 하면 RAG를 사용하는 것이 더 좋다고 판단할 수 있습니다.

### LoRA VS QLoRA

unsloth의 dynamic 4it quatization덕분에 QLoRA써도 정확도 손실 무시할 수 있습니다.

### 결국은 '실험'

fine tuning에서 최고의 접근법은 없다고 합니다. 다양한 시나리오에 대한 모범사례만 존재하기에 데이터셋과 사용 목적에 따라 실험을 통해 최적의 방법을 찾아야합니다.

### 데이터셋의 크기

- 1,000개 이상의 행이 있는 데이터 : 1,000개가 넘는 행이 있는 대규모 데이터 세트가 있는 경우 일반적으로 기본 모델을 미세 조정하는 것이 가장 좋습니다.
- 300~1,000행의 고품질 데이터 : 기본 모델이나 지시 모델을 미세 조정하는 것이 모두 실행 가능한 상황입니다.
- 300개 행 미만 : 데이터 세트가 작을 경우 일반적으로 instruct 모델을 사용해야합니다.

### 계획

성능 평가를 위해 정량적 벤치마크를 사용할 수도 있지만 학습목적에는 과하다고 생각해서 LLM Judge를 사용하기로 하였습니다.

또한 실제 서비스가 아니어서 Ground truth를 golden set으로 사용하기 어려워 huggingface data를 train과 test로 나누었습니다.\

1. Golden set 구축
2. Base line 추론
3. Fine tuning (with WandB)
4. Fine tuned 추론 및 GPT 활용하여 Judge
5. vLLM 서빙
